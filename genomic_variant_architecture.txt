
Genomic Variant Interpretation Database Architecture
Production-Ready SQL Schema Design for InterVar and ClinGen ERepo Integration

1. Executive Summary
This document proposes a production-grade PostgreSQL schema architecture optimized for genomic variant interpretation systems integrating InterVar, ClinGen ERepo, ClinVar, and ACMG Evidence Framework.

2. System Objectives
- Variant-level search
- Clinical interpretation management
- Explainability and AI integration

3. Architectural Design Principles
- SQL-first design
- Hybrid flat + normalized architecture
- Provenance preservation
- Explainability readiness

4. Core Database Tables
- variants
- genes
- conditions
- variant_interpretations
- interpretation_evidence_lines
- criterion_assessments
- evidence_references
- curation_agents
- column_dictionary
- acmg_rule_map

5. Variants Table
Stores searchable genomic variants with:
- chromosome
- start_pos
- end_pos
- ref_allele
- alt_allele
- rsid
- caid
- gene_symbol
- hgvs_c
- hgvs_p
- clinvar_significance
- intervar_classification

6. ACMG Interpretation Modeling
Supports:
- PP4
- PM2
- PM6
- PS4
with evidence strengths such as supporting, moderate, and strong.

7. Suggested PostgreSQL Schema

variant_id BIGSERIAL PRIMARY KEY,
chromosome VARCHAR(5),
start_pos BIGINT,
end_pos BIGINT,
ref_allele TEXT,
alt_allele TEXT,
gene_symbol TEXT,
hgvs_c TEXT,
hgvs_p TEXT,
clinvar_significance TEXT,
intervar_classification TEXT,
raw_row_json JSONB,
created_at TIMESTAMP,
updated_at TIMESTAMP

8. Recommended Indexes
- (chromosome, start_pos, end_pos)
- rsid
- gene_symbol
- clinvar_significance
- intervar_classification

9. Final Recommendation
Do not store only raw ERepo JSON in one table.
Do not create one large denormalized mega-table.
Maintain normalized evidence structures while preserving flat searchable variant records.

This architecture supports SQL-first genomic querying, explainability, provenance tracking, and future LLM-based genomic interpretation systems.
